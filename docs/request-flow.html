③ GenerationWorker.processPendingJobs (폴링, 기본 500ms) INFRA
GenerationWorker.processPendingJobs
job/worker/GenerationWorker.java · @ConditionalOnExpression(app.scheduling.enabled and app.worker.enabled)
  • @Scheduled(fixedDelay = app.scheduling.worker-interval-millis, 기본 500ms)
  • findByStatusOrderByIdAsc(HOLDING, PageRequest.of(0, app.worker.batch-size)) — 한 주기 조회 상한 20건. jobs(status, id) 인덱스가 이 조회를 받쳐준다
  • job마다 선점(claim) 후 위임(dispatch) 순서로 처리한다 — 슬롯을 미리 확보하지 않는다. 선점에 성공한 job만 generationWorkerExecutor에 위임을 시도하고, 위임이 거부되면 그 job을 HOLDING으로 롤백한 뒤 이번 주기를 즉시 중단한다 (남은 job은 다음 폴링에서 다시 조회된다)
  • jobRepository.startProcessingIfAttemptMatches(jobId, attemptNo, now)
    UPDATE job SET status='PROCESSING' WHERE id=? AND status='HOLDING' AND attempt_no=? — 선점 + attemptNo fencing. 0행이면 다른 워커가 이미 가져갔거나 무효한 시도이므로 건너뛴다. 여러 인스턴스가 같은 목록을 읽어도 실행은 하나뿐
  • 선점 성공분만 generationWorkerExecutor로 위임. 위임이 거부되면 transitionIfStatusAndAttemptMatch(HOLDING ← PROCESSING)으로 즉시 되돌려 다음 폴링에서 다시 잡히게 한다 (롤백마저 실패하면 ⑦의 timeout 회수에 맡긴다)
④ generationWorkerExecutor (실행 슬롯) INFRA
WorkerExecutorConfig.generationWorkerExecutor
job/worker/WorkerExecutorConfig.java · job/worker/WorkerProperties.java
  • core/max pool = app.worker.concurrency(3), queueCapacity = 0 — executor는 대기열을 갖지 않는다. 대기열 역할은 DB의 HOLDING 상태가 한다
  • 동시 실행 상한은 executor 혼자 지킨다 — queueCapacity가 0 이하면 Spring의 ThreadPoolTaskExecutor는 내부적으로 SynchronousQueue를 쓰므로, 스레드 3개가 모두 사용 중일 때 execute()를 호출하면 TaskRejectedException이 던져진다 — 이 거부가 ③의 롤백·주기 중단 신호가 된다
  • 폴링 스레드와 분리된 풀(generation-worker-*)이라 3~7초짜리 외부 호출이 스케줄러를 붙들지 않는다. spring.task.scheduling.pool.size=2로 워커 폴링과 ⑦의 스캔도 서로 밀리지 않게 분리
  • WorkerProperties가 batch-size·concurrency를 기동 시점에 검증한다 (1 미만이면 시작 실패)

DeadJobSchedulerTask.scan

  • 1. heartbeatRegistry.findExpiredJobIds() → markExpiredJobsAsFailed(): heartbeat 만료된 PROCESSING job을 FAILED로 전이 (워커 크래시 회수)
  • 2. reapStaleProcessing(): app.processing.timeout-seconds(60초) 넘은 PROCESSING job 중 살아있는 heartbeat가 없는 것만 FAILED로 회수 (Redis 장애 / 선점 직후 위임·롤백 실패 / heartbeat 등록 전 크래시 / ⑤의 confirm 재시도 소진을 모두 커버)

3핵심 설계 원칙: 조건부 연산

check-then-act(조회 후 판단 후 실행) 대신, 확인과 실행을 조건부 UPDATE/INSERT 하나로 원자화한다. 동시성 문제를 락이 아니라 SQL의 원자성으로 해결.

문제 상황조건부 연산
동시 잔액 차감 
UPDATE organization SET balance = balance - :amount
WHERE id = :id AND balance >= :amount
-- deductBalance
잔액 증액 (환불/충전) 
UPDATE organization SET balance = balance + :amount
WHERE id = :id
-- addBalance
이중 결과 쓰기 (재시도 워커 vs 원래 워커) 
UPDATE job SET status = ?
WHERE id = ? AND attempt_no = ?
-- attemptNo fencing
중복 요청 
-- idempotency_keys 의 (org_id, idem_key) unique 제약
-- 위반을 중복 판정으로 사용
최종 refund vs 늦은 워커 성공 
UPDATE job SET status = 'REFUNDED'
WHERE id = ? AND status = 'FAILED' AND attempt_no = ?
스케줄러 다중 인스턴스 재시도 경합 
UPDATE job SET attempt_no = attempt_no + 1
WHERE id = ? AND status = 'FAILED' AND attempt_no = ?
